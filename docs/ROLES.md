# 誰實作、誰審查

常見問題：強模型實作、便宜模型審查，或反過來，哪個又省又好？答案是看任務難度，兩種固定配對都不是最佳解。

| 做法 | 品質 | Token | 適合 |
| --- | --- | --- | --- |
| 強模型實作 + 便宜模型審查 | 高，品質由實作者決定 | 中。強模型在長對話裡寫；審查便宜，但誤判會讓強模型白改 | 困難、需求模糊、要全局判斷 |
| 便宜模型實作 + 強模型審查 | 簡單任務夠用，困難任務差 | 簡單任務最省；困難任務最貴，便宜模型反覆寫錯、強模型每輪都要審 | 規格清楚、有測試能驗收 |

## 原因

1. **審查只能攔錯，不能把程式變好。** 品質上限由實作者決定。弱模型寫難題，強審查者只會一直退回，輪數暴增。
2. **強模型單次審查比在主對話裡實作省。** MAF 的 reviewer 每次都是新 session，只讀 diff 與相關檔案，不累積對話；主對話每一輪都要重讀整段長 context。
3. **最便宜的審查者是測試。** 測試不會誤判、不花 token。[基準測試](../bench/effort/README.md)裡，便宜 coder 在有測試把關時一次就能通過。
4. **沒有停止條件的迴圈才是真正的浪費。** 「審查者有任何意見就退回」加上「沒有輪數上限」，一個 PR 就可能跑十幾輪，這和誰寫誰審無關。

## MAF 怎麼套用

- **規格清楚、測試能驗收**：`delegate` 給便宜 coder，測試把關，主對話只看 diff。
- **困難或模糊**：主對話自己實作並 commit，再用 `verify`。要第二雙眼睛就在 flow 開啟獨立審查（和主對話不同家）。`verify` 審查不通過時停下來由主對話修，不會自動來回。
- **迴圈有上限**：`max_repairs` 預設 1、最多 5，用完停在 `needs_human`。
- **只有能證明的問題會擋**：審查的 `findings` 只放能在程式碼中證明的正確性、安全或回歸問題，會觸發修復；疑慮與建議放 `notes`，不擋 approve，由主對話在 `handoff` 判斷。
